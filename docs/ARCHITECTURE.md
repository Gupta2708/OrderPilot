# OrderPilot architecture

## Foundation and intended boundaries

```text
Next.js App Router + Tailwind
             |
             v
FastAPI control plane --------> PostgreSQL product records
             |
             v
Temporal client -> Temporal service -> Python worker
                                          |
                                  Workflow / Activities
```

Stage 0 implemented the application shells, typed configuration, database schema, and Temporal connection. Stage 1 added `OrderSupervisorWorkflow`: one durable workflow per order owning lifecycle, Signal handling, durable timers, and completion rules. Stage 2 added the agent runtime behind that lifecycle. Stage 3 added persistence and the FastAPI control plane. Stage 4 added the operations UI, completing P0. Stage 5 added the P1 layer: a hybrid wake policy, a human approval gate, and a demonstrated durability story. Stage 6 added P2: analytics, adaptive wake guidance, Continue-As-New, and supervisor templates. Stage 7 is final hardening, documentation, and submission readiness.

Activities contain LLM inference, business actions, memory compaction, final-summary generation, and database writes. Network and database operations stay outside replayed workflow code; the workflow performs no I/O at all. PostgreSQL holds the product-facing record — runs, unified timeline, memory, decisions, final outputs — while Temporal owns durable execution history. The two are deliberately separate: Temporal is the execution truth, Postgres is the product truth.

## Stage 1 workflow core

```text
start_workflow(order) --> OrderSupervisorWorkflow (id: order-supervisor:<order_id>)
                              |
     Signals ----------------->|  order_event / add_instruction / pause / resume / terminate
     Queries <-----------------|  state / timeline
                              |
                              v
                    wake on start | important Signal | durable timer
                              |
                              v
                    deterministic wake policy  -> WAKE_DECISION
                              |
                              v
                    agent decision             -> AGENT_DECISION
                              |
                              v
                    durable sleep until next review
                              |
                              v
                    workflow-owned terminal rule -> FINAL_OUTPUT
```

Layering keeps Temporal-specific code thin. `app/domain/` holds pure, deterministic logic — event parsing, structured order state, the wake policy, the decision maker, and lifecycle rules — with no I/O, clock reads, or randomness, so it is both replay-safe inside the workflow sandbox and testable without a Temporal server. `app/temporal/` holds only the workflow, worker, client, and I/O contracts.

The workflow never polls. It waits on `workflow.wait_condition` with a timeout derived from the earlier of the next scheduled review and the maximum run age, so it is woken by a Signal or by a durable timer and by nothing else. A paused run stops processing events but remains terminable, and a terminal run clears its next wake so it can never schedule another.

Lifecycle authority is deliberately separated from decision making. The decision object carries `completion_recommended`, but only the workflow's own rules — a terminal event, a `terminate` Signal, or the maximum age — actually end a run. Stage 2 swaps the placeholder decision maker for an Agent Activity returning the same shape without touching those rules.

Events are validated inside the Signal handler and de-duplicated by `event_id`, so a malformed or repeated Signal is recorded on the timeline instead of corrupting state. Unknown event types are escalated rather than dropped.

The three product tables separate reusable supervisor configuration, order run snapshots, and a unified activity log. Activity records are append-only; nothing updates or deletes a timeline row. The final-output JSON will hold summary, important actions, learnings, and recommendations. Timestamps use timezone-aware PostgreSQL columns; UUIDs are generated by the application.

The five actions explicitly listed on PDF page 13 are `message_fulfillment_team`, `message_payments_team`, `message_logistics_team`, `message_customer`, and `create_internal_note`. Stage 2 executes them as simulated Activities, each returning a structured success/failure result recorded on the timeline. Page 14 requires workflow-owned completion, implemented as explicit terminal rules in workflow code.

## Stage 2 agent runtime

```text
workflow wake
     |
     v
make_decision Activity -> provider (mock | openrouter | claude) -> Pydantic validation
     |                                                          |
     |                          retry once, then deterministic fallback
     v
allow-list filter  -> rejected tools recorded, never executed
     |
     v
run_business_action Activity (x N)  -> structured ok/failure per action
     |
     v
compact_run_memory Activity -> compact rolling memory
     |
     v
workflow schedules the next durable sleep
```

Four Activities own everything non-deterministic: `make_decision`, `run_business_action`, `compact_run_memory`, and `finalize_run`. The workflow calls them with explicit timeouts and retry policies and stores only their results, which keeps replay deterministic even though the underlying work is not.

The decision contract is a Pydantic model, so model output is validated before it can influence anything. Tool names are a closed enum in the schema itself, which means an invented tool fails validation rather than reaching the allow-list. Validated output is then normalised inside the Activity: the sleep specification collapses to a bounded integer number of minutes, and every proposed tool is filtered against the supervisor's allowed actions. Rejections are recorded on the timeline instead of being dropped silently, and an `ACT` whose every tool was rejected is downgraded to `NO_ACTION` so the decision cannot claim an action it never took. Execution re-checks the allow-list a third time, so no code path can reach a tool the supervisor does not permit.

Three providers implement one interface, and the workflow knows about none of them. `ClaudeProvider` uses the Anthropic SDK's structured-output parse endpoint with server-side refusal fallbacks. `OpenRouterProvider` uses the OpenAI SDK against OpenRouter's OpenAI-compatible endpoint, which is the path available when the credential is an OpenRouter key. `MockProvider` is deterministic, needs no key or network, and reuses the same policy the workflow was proven against in Stage 1 — it is a supported demo mode, not just a test double. Malformed output, a refusal, or a transport failure is retried once and then replaced by a deterministic fallback that never acts.

Action arguments are given an explicit schema rather than a free-form object. A bare `dict[str, Any]` gives the model nothing to fill in and it reliably returns `{}`, which silently reduced every message to a generic default — the model could take an action but never actually say anything. Naming `message` and `note` in the schema fixed it, and the difference is visible in the messages the agent now writes.

Memory stays deliberately small and deterministic: an append-with-cap that keeps the most recent notes, marks how many were compacted away, and length-caps the whole summary. A summarising LLM call here would add cost and non-determinism for little benefit at this size.

The agent's context is assembled per decision from the supervisor instruction, live run instructions, structured order state, compact memory, the triggering event, the wake evaluation, a short recent-activity window, and the allowed actions. Full raw history is never sent.

Lifecycle authority is unchanged from Stage 1 and is tested explicitly: a provider that recommends completion on every decision cannot end a run, and only a terminal event, a `terminate` Signal, or the maximum age does.

## Stage 3 control plane and persistence

```text
          Next.js operations UI
                 |
                 v
       FastAPI control plane
        |                   |
        | reads             | start_workflow / Signals / Queries
        v                   v
   PostgreSQL <------ Temporal workflow
        ^                   |
        |                   v
        +-------- persist_snapshot Activity
```

Reads and writes take different paths, on purpose. The API never writes run progress itself: it starts workflows and sends Signals, and the workflow persists its own state through the `persist_snapshot` Activity. That keeps one writer for run progress and avoids the API and the workflow racing to describe the same run.

A persistence failure never stops supervision. Temporal owns execution truth and Postgres only mirrors it for the product, so if the mirror is unavailable the run keeps deciding and acting, the buffered rows stay buffered, and the write is retried at the next flush. Because unflushed rows would otherwise re-wake the run loop immediately, a failed write also sets a flag that stops them from doing so, which prevents a spin.

The workflow buffers timeline rows and flushes them with current run state at natural boundaries: after the start wake, after each event drain, after each scheduled review, before parking on a pause, and at finalization. One durable write covers a whole wake cycle rather than one per timeline row. The buffer is cleared only after the Activity succeeds, so a failed write is retried with the same rows instead of losing them. Because a Signal can write a timeline row without producing work — a duplicate event, a rejected event, an instruction while the run is idle — the wait condition also wakes on unflushed rows, so those reach Postgres promptly instead of waiting for the next event.

Each row carries a per-run sequence number under a unique `(run_id, seq)` constraint, and inserts ignore conflicts. A retried persistence Activity therefore cannot duplicate history, which matters because Temporal will retry it.

`GET /api/runs/{id}/state` prefers a live Query to the workflow and falls back to the persisted snapshot when the workflow has closed or Temporal is unreachable, labelling which source answered. `GET /api/runs/{id}` always answers from Postgres, so the timeline and final output remain available long after the workflow has completed and aged out of Temporal.

Layering keeps HTTP thin. `app/repository.py` owns database access, `app/services/runs.py` owns the mapping from product operations to Temporal operations, and `app/api/` contains only routing, validation, and error translation. Business logic is therefore testable without HTTP handlers, which is how the API suite runs against a real database with a faked Temporal client, while `tests/test_end_to_end.py` exercises the real thing.

## Stage 4 user interface

The UI is a thin client. It holds no business logic and no lifecycle rules: it renders what the API reports and turns operator intent into API calls. Everything it shows already exists in the workflow or the database, which is why the same story can be told through `curl` without it.

Screens map onto the domain rather than onto the API: a dashboard bucketing runs by what they are doing, supervisor configuration, a start-run flow, and the Run Control Room. The control room is the point of the product, so it puts the durable-execution story on one screen — current status, the countdown to the next durable wake, structured order state, compact memory, the decision the agent made, the wake decision explaining why the agent was or was not consulted, the unified timeline, and the actions actually executed.

Two API reads back it. `GET /api/runs/{id}` supplies the persisted record, including the timeline and final output, and remains available after the workflow closes. `GET /api/runs/{id}/state` supplies live workflow state and labels its source, so the screen shows whether it is reading the workflow or the database. Where both carry a field, live state wins and the persisted record is the fallback.

The client polls every two seconds rather than opening a stream. Runs advance on their own — a timer fires, an event arrives — so the screen has to change without user action, and at POC scale against a local API, polling is the smaller, more debuggable choice. One `usePolling` hook owns that behaviour so no screen re-implements it.

The event simulator exists to make the wake policy visible. Injecting `payment_confirmed` updates the order state while the wake card explains that the main agent was deliberately not consulted; injecting `shipment_delayed` wakes it and produces an escalation. That contrast is the clearest demonstration that Temporal, not the model, owns the loop. Scenario presets advance one step at a time so each wake decision can be read before the next event lands, and the injector deliberately offers an unrecognised event type so unknown-event escalation can be shown.

Controls are asynchronous and the UI says so. Pause, resume, terminate, events, and instructions are Signals; the API returns 202 and the workflow applies them on its next step, so the screen reports the request as accepted and lets the next poll show the effect rather than faking an immediate state change. Chain-of-thought is never displayed — only the stored reason summary.

## Stage 5 wake policy and approvals

```text
event arrives
     |
     v
Level A: deterministic table  --- known lifecycle event ---> wake / no-wake
     |
     | unknown type, or a customer message
     v
Level B: classify_event Activity -> structured verdict -> validated
     |                                     |
     |                     failure -> deterministic fallback
     v
severity capped by the supervisor's wake sensitivity
     |
     v
WAKE_DECISION recorded with the rule that produced it
```

The two levels exist for different reasons. Level A is free, instant, and covers the events whose meaning is fixed by the domain, so the common path never pays for inference. Level B exists because two categories genuinely cannot be answered by a table: an unrecognised event type, which the system has no rule for, and a customer message, whose meaning lives in the text. Sending everything to the classifier would be wasteful; sending nothing would mean hard-coding judgements the system cannot actually make.

The classifier never gets the last word on its own. Its severity is capped by the supervisor's wake sensitivity, so a `LOW`-severity verdict cannot wake a `BALANCED` supervisor even if the model asks for it, and a failure falls back to deterministic evaluation. Unknown events escalate rather than disappear. Every verdict is recorded with the rule that produced it — `deterministic_severity_table`, `ai_classifier:<provider>`, or `classifier_fallback_deterministic` — so the timeline always shows which layer decided and why.

```text
decision proposes an action
     |
     v
tool in the supervisor's require_approval_for?
     |                          |
     no                        yes
     |                          v
     v            ACTION_PENDING_APPROVAL, status AWAITING_APPROVAL
 execute now                    |
                    approve_action  /  reject_action  (Signals)
                          |                  |
                          v                  v
                    ACTION_APPROVED     ACTION_DENIED
                          |             (never executed)
                          v
                    execute the action
```

The approval gate sits between deciding and executing, which is the only place it can be correct. The agent still proposes normally; the workflow holds the action, and human intent arrives as ordinary Signals like every other control. Approved actions are queued and executed by the run loop rather than inside the Signal handler, so execution stays on the deterministic path. A rejected action is recorded and dropped — there is no code path from a rejection to an execution.

Durability needed no new mechanism, only a demonstration. Because state lives in Temporal rather than the worker, a run survives its worker disappearing entirely: Signals sent during the outage are held and delivered when a worker returns. The automated test leaves the task queue genuinely unattended, sends an event into that gap, and asserts the run resumes with its memory and history intact.

## Stage 6 analytics, guidance, and Continue-As-New

Analytics are derived, not stored twice. The workflow already maintains counters as it runs and persists them with each snapshot, so the analytics endpoint reads the run row and computes the two ratios worth reading — wake rate and actions per wake — rather than maintaining a separate aggregate that could drift. Wake rate deliberately counts only signal-driven wakes: the start wake and scheduled reviews are not responses to events, and including them would overstate how often the agent was actually needed.

Adaptive guidance closes a loop that was previously one-way. The classifier could consume standing guidance from the beginning, but nothing produced any; now the agent may emit up to three short hints, which are cleaned, de-duplicated, length-capped, persisted, and supplied to later classifications. The boundary matters: guidance is advisory input to triage, never authority. It cannot add a tool to the allow-list, and it cannot lower the supervisor's wake threshold — those remain configuration, checked after the classifier has spoken.

```text
run reaches its event threshold at a quiet point
     |
     v
record RUN_CONTINUED  ->  persist (timeline is safe in Postgres)
     |
     v
carry compact state:
  order state | memory | instructions | guidance | counters
  executed actions | pending approvals | queued events | recent event ids
     |
     v
workflow.continue_as_new(params)  ->  fresh history, same run identity
```

Continue-As-New keeps a long-lived order's Temporal history bounded. What it carries is deliberately small — current state, not history — because the timeline already lives in PostgreSQL, and carrying it would defeat the purpose. Run identity is preserved: same order ID, same run ID, same workflow ID, so the product record and the UI see one continuous run.

Two details are what make it safe. First, a continuation only happens at a quiet point — no queued events, no approved actions waiting to execute, nothing pending a human, not paused, not terminal — because resetting history mid-decision would strand work. Second, the persist call inside the continuation awaits, which yields and lets Signal handlers run, so events can be queued in that exact window; they are carried across rather than dropped. That path is covered by a direct round-trip test of the carried state, because losing a Signal here would be silent, and silence is the worst failure mode this system can have.

The seen-event-id tail is bounded and ordered by insertion, so de-duplication survives the boundary for recent events without carrying every id the run has ever seen.

## Local deployment

Frontend, API, and worker run as local processes. Docker Compose runs PostgreSQL and the Temporal development server with separate persistent volumes. Only loopback ports are published. The backend reads root `.env` through Pydantic Settings; no secrets are put in browser code.

The worker registers `OrderSupervisorWorkflow` and one asynchronous infrastructure activity. Its smoke mode validates startup and shutdown only. Workflow lifecycle behaviour is covered instead by tests against Temporal's time-skipping test server, which exercises durable timers without waiting in real time.

## Tradeoffs, and why

A few choices were made deliberately and are worth defending rather than hiding.

**Postgres and Temporal both hold state, on purpose.** Temporal owns execution truth; Postgres owns the product record. The duplication is real, but the alternative is worse: reading a completed run's timeline out of Temporal history couples the product to an execution engine's retention, and writing product state from the API would put two writers on the same run. The workflow is the single writer, and a persistence failure is non-fatal, because a reporting outage must not stop supervision.

**The rule layer exists to avoid inference, not to encode the business.** It covers only events whose meaning is fixed by the domain, and defers anything genuinely ambiguous. That keeps the common path free while leaving judgement to the model where judgement is actually required.

**The classifier never has the last word.** Its severity is capped by configuration, and any failure falls back to deterministic rules. A triage layer that can fail open into "wake for everything" or fail closed into "wake for nothing" would be worse than no classifier at all.

**Memory is truncation, not summarization.** A summarising call per wake would add cost, latency, and non-determinism to every cycle, for a summary that is currently a handful of lines. It is the right call at this size and the wrong one at ten times it.

**Polling in the UI, not streaming.** Two seconds against a local API is small and debuggable. Streaming would be the correct answer for many concurrent operators.

**Actions are simulated.** The assignment permits it, and real integrations would add credentials and failure modes without demonstrating anything about durable orchestration.

**What would come next**, in order: an approvals queue across runs rather than per-run state; cross-run analytics per supervisor; pagination and authentication; classifier caching for message bursts; editable supervisors; and exercising the Anthropic provider against a live key, since only the OpenRouter path has been proven at runtime.
