# OrderPilot architecture

## Foundation and intended boundaries

```text
Next.js App Router + Tailwind
             |
             v
FastAPI control plane --------> PostgreSQL product records
             |
             v
Temporal client -> Temporal service -> Python worker
                                          |
                                  Workflow / Activities
                                  (later stages)
```

Stage 0 implements the application shells, typed configuration, database schema, Temporal connection, and an activity-only worker. The arrows to business operations describe the intended architecture; there is no order workflow or run-management API yet.

In subsequent stages, one Temporal workflow per order will own lifecycle, signal handling, durable timers, and completion rules. Activities will contain LLM inference, business actions, and persistence side effects. Network and database operations must stay outside replayed workflow code. PostgreSQL will hold the product-facing timeline and compact memory; Temporal will own durable execution history.

The three product tables separate reusable supervisor configuration, order run snapshots, and a unified activity log. Activity records are intended to be appended; Stage 0 exposes no mutation API. The final-output JSON will hold summary, important actions, learnings, and recommendations. Timestamps use timezone-aware PostgreSQL columns; UUIDs are generated by the application.

The five actions explicitly listed on PDF page 13 are `message_fulfillment_team`, `message_payments_team`, `message_logistics_team`, `message_customer`, and `create_internal_note`. They will be simulated and recorded as activities. Page 14 requires workflow-owned completion, clarifying the earlier generic tool examples. Neither actions nor lifecycle rules are implemented in this stage.

## Local deployment

Frontend, API, and worker run as local processes. Docker Compose runs PostgreSQL and the Temporal development server with separate persistent volumes. Only loopback ports are published. The backend reads root `.env` through Pydantic Settings; no secrets are put in browser code.

The worker has one asynchronous infrastructure activity so the SDK can start and poll without registering an order workflow. Its smoke mode validates startup/shutdown only, not workflow durability or business execution.
