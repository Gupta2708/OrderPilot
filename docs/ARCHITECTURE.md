# OrderPilot architecture

## Foundation and intended boundaries

```text
Next.js App Router + Tailwind
             |
             v
FastAPI control plane --------> PostgreSQL product records
             |
             v
Temporal client -> Temporal service -> Python worker
                                          |
                                  Workflow / Activities
                                  (later stages)
```

Stage 0 implemented the application shells, typed configuration, database schema, and Temporal connection. Stage 1 added `OrderSupervisorWorkflow`: one durable workflow per order owning lifecycle, Signal handling, durable timers, and completion rules. Stage 2 added the agent runtime behind that lifecycle. Stage 3 adds persistence and the FastAPI control plane, completing the P0 backend.

Activities contain LLM inference, business actions, memory compaction, final-summary generation, and database writes. Network and database operations stay outside replayed workflow code; the workflow performs no I/O at all. PostgreSQL holds the product-facing record — runs, unified timeline, memory, decisions, final outputs — while Temporal owns durable execution history. The two are deliberately separate: Temporal is the execution truth, Postgres is the product truth.

## Stage 1 workflow core

```text
start_workflow(order) --> OrderSupervisorWorkflow (id: order-supervisor:<order_id>)
                              |
     Signals ----------------->|  order_event / add_instruction / pause / resume / terminate
     Queries <-----------------|  state / timeline
                              |
                              v
                    wake on start | important Signal | durable timer
                              |
                              v
                    deterministic wake policy  -> WAKE_DECISION
                              |
                              v
                    placeholder decision       -> AGENT_DECISION, ACTION_PROPOSED
                              |
                              v
                    durable sleep until next review
                              |
                              v
                    workflow-owned terminal rule -> FINAL_OUTPUT
```

Layering keeps Temporal-specific code thin. `app/domain/` holds pure, deterministic logic — event parsing, structured order state, the wake policy, the decision maker, and lifecycle rules — with no I/O, clock reads, or randomness, so it is both replay-safe inside the workflow sandbox and testable without a Temporal server. `app/temporal/` holds only the workflow, worker, client, and I/O contracts.

The workflow never polls. It waits on `workflow.wait_condition` with a timeout derived from the earlier of the next scheduled review and the maximum run age, so it is woken by a Signal or by a durable timer and by nothing else. A paused run stops processing events but remains terminable, and a terminal run clears its next wake so it can never schedule another.

Lifecycle authority is deliberately separated from decision making. The decision object carries `completion_recommended`, but only the workflow's own rules — a terminal event, a `terminate` Signal, or the maximum age — actually end a run. Stage 2 swaps the placeholder decision maker for an Agent Activity returning the same shape without touching those rules.

Events are validated inside the Signal handler and de-duplicated by `event_id`, so a malformed or repeated Signal is recorded on the timeline instead of corrupting state. Unknown event types are escalated rather than dropped; Stage 5 adds the lightweight classifier that will handle the ambiguous cases the deterministic table defers.

The three product tables separate reusable supervisor configuration, order run snapshots, and a unified activity log. Activity records are append-only; nothing updates or deletes a timeline row. The final-output JSON will hold summary, important actions, learnings, and recommendations. Timestamps use timezone-aware PostgreSQL columns; UUIDs are generated by the application.

The five actions explicitly listed on PDF page 13 are `message_fulfillment_team`, `message_payments_team`, `message_logistics_team`, `message_customer`, and `create_internal_note`. Stage 2 executes them as simulated Activities, each returning a structured success/failure result recorded on the timeline. Page 14 requires workflow-owned completion, implemented as explicit terminal rules in workflow code.

## Stage 2 agent runtime

```text
workflow wake
     |
     v
make_decision Activity ---> provider (mock | claude) ---> Pydantic validation
     |                                                          |
     |                          retry once, then deterministic fallback
     v
allow-list filter  -> rejected tools recorded, never executed
     |
     v
run_business_action Activity (x N)  -> structured ok/failure per action
     |
     v
compact_run_memory Activity -> compact rolling memory
     |
     v
workflow schedules the next durable sleep
```

Four Activities own everything non-deterministic: `make_decision`, `run_business_action`, `compact_run_memory`, and `finalize_run`. The workflow calls them with explicit timeouts and retry policies and stores only their results, which keeps replay deterministic even though the underlying work is not.

The decision contract is a Pydantic model, so model output is validated before it can influence anything. Tool names are a closed enum in the schema itself, which means an invented tool fails validation rather than reaching the allow-list. Validated output is then normalised inside the Activity: the sleep specification collapses to a bounded integer number of minutes, and every proposed tool is filtered against the supervisor's allowed actions. Rejections are recorded on the timeline instead of being dropped silently, and an `ACT` whose every tool was rejected is downgraded to `NO_ACTION` so the decision cannot claim an action it never took. Execution re-checks the allow-list a third time, so no code path can reach a tool the supervisor does not permit.

Two providers implement one interface. `ClaudeProvider` uses the Anthropic SDK's structured-output parse endpoint with `claude-opus-5` and server-side refusal fallbacks. `MockProvider` is deterministic, needs no key or network, and reuses the same policy the workflow was proven against in Stage 1 — it is a supported demo mode, not just a test double, and it is the default. Malformed output, a refusal, or a transport failure is retried once and then replaced by a deterministic fallback that never acts.

Memory stays deliberately small and deterministic: an append-with-cap that keeps the most recent notes, marks how many were compacted away, and length-caps the whole summary. A summarising LLM call here would add cost and non-determinism for little benefit at this size.

The agent's context is assembled per decision from the supervisor instruction, live run instructions, structured order state, compact memory, the triggering event, the wake evaluation, a short recent-activity window, and the allowed actions. Full raw history is never sent.

Lifecycle authority is unchanged from Stage 1 and is tested explicitly: a provider that recommends completion on every decision cannot end a run, and only a terminal event, a `terminate` Signal, or the maximum age does.

## Stage 3 control plane and persistence

```text
          Next.js (Stage 4)
                 |
                 v
       FastAPI control plane
        |                   |
        | reads             | start_workflow / Signals / Queries
        v                   v
   PostgreSQL <------ Temporal workflow
        ^                   |
        |                   v
        +-------- persist_snapshot Activity
```

Reads and writes take different paths, on purpose. The API never writes run progress itself: it starts workflows and sends Signals, and the workflow persists its own state through the `persist_snapshot` Activity. That keeps one writer for run progress and avoids the API and the workflow racing to describe the same run.

The workflow buffers timeline rows and flushes them with current run state at natural boundaries: after the start wake, after each event drain, after each scheduled review, before parking on a pause, and at finalization. One durable write covers a whole wake cycle rather than one per timeline row. The buffer is cleared only after the Activity succeeds, so a failed write is retried with the same rows instead of losing them. Because a Signal can write a timeline row without producing work — a duplicate event, a rejected event, an instruction while the run is idle — the wait condition also wakes on unflushed rows, so those reach Postgres promptly instead of waiting for the next event.

Each row carries a per-run sequence number under a unique `(run_id, seq)` constraint, and inserts ignore conflicts. A retried persistence Activity therefore cannot duplicate history, which matters because Temporal will retry it.

`GET /api/runs/{id}/state` prefers a live Query to the workflow and falls back to the persisted snapshot when the workflow has closed or Temporal is unreachable, labelling which source answered. `GET /api/runs/{id}` always answers from Postgres, so the timeline and final output remain available long after the workflow has completed and aged out of Temporal.

Layering keeps HTTP thin. `app/repository.py` owns database access, `app/services/runs.py` owns the mapping from product operations to Temporal operations, and `app/api/` contains only routing, validation, and error translation. Business logic is therefore testable without HTTP handlers, which is how the API suite runs against a real database with a faked Temporal client, while `tests/test_end_to_end.py` exercises the real thing.

## Local deployment

Frontend, API, and worker run as local processes. Docker Compose runs PostgreSQL and the Temporal development server with separate persistent volumes. Only loopback ports are published. The backend reads root `.env` through Pydantic Settings; no secrets are put in browser code.

The worker registers `OrderSupervisorWorkflow` and one asynchronous infrastructure activity. Its smoke mode validates startup and shutdown only. Workflow lifecycle behaviour is covered instead by tests against Temporal's time-skipping test server, which exercises durable timers without waiting in real time.
